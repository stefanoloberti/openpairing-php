# Exact THP evidence execution runbook

This runbook is the ordered, fail-closed procedure for producing evidence from
the exact ChessPairings candidate that embeds OpenPairingPHP. It is not a
deployment procedure and authorizes no production access. Use only an isolated
application instance, synthetic tournaments and a disposable database.

The acceptance contracts remain normative in
`THP-INTEGRATION-CONTRACT.md`, `THP-PRODUCT-ACCEPTANCE-PLAN.md` and
`SHADOW-VALIDATION.md`. This document fixes execution order and promotion
rules so independently green reports cannot be combined across identities.

## Exit classes

All verifier output is machine-readable JSON.

| Exit | Meaning | Required action |
|---|---|---|
| `0` | The supplied evidence passed that verifier | Preserve report and hashes; continue only if identity is unchanged |
| `1` | Honest `NO_GO` or review-required result | Quarantine the batch; diagnose outside production; do not promote later reports as a complete bundle |
| `2` | Infrastructure or malformed-evidence error | Treat the observation as absent; repair the harness and repeat under a new evidence-run ID |

An empty report, missing scenario, wrong denominator or unobserved product path
is never a pass.

## Immutable run directory

Create one new directory outside the product source tree for each attempt:

```text
thp-evidence/<candidate-identity>/<run-id>/
  candidate.json
  artifacts/
  inputs/
  batches/
  reports.tmp/
  reports/
  hashes.json
```

The run ID is unique and is not reused after any source, migration, mapping,
runtime, package or configuration-contract change. Raw reports are first
written under `reports.tmp`. A report moves to `reports` only after its
verifier exits `0`, its JSON parses, its status is the expected positive
status, and its SHA-256 is recorded. Never overwrite a promoted file.

The evidence directory contains no player names, e-mail addresses, FIDE IDs,
credentials or source-list rows. Only synthetic counters, pseudonymous IDs and
hashes allowed by the schemas may leave the isolated environment.

## 1. Freeze product source and migrations

Start from a clean, source-controlled ChessPairings candidate. List every
migration directory that can affect the submitted build:

```console
php tools/verify_thp_source_freeze.php PRODUCT_ROOT MIGRATION_PATH [MIGRATION_PATH ...]
```

Require `openpairing.thp-source-freeze-verification/1`, status `PASS`, zero
secret findings and unchanged Git HEAD before/after the scan. Record
`sourceCommit`, `sourceManifestSha256` and `migrationManifestSha256`.

If the product checkout is dirty, has untracked source, lacks a migration path
or contains a sensitive-value finding, stop. Do not manufacture a candidate
identity from a partially observed tree.

## 2. Build and verify the candidate identity

Build the installer, OpenPairing runtime, PTC and RTG from that frozen tree,
then create `openpairing.thp-candidate-identity/1`:

```console
php tools/verify_thp_candidate_identity.php candidate.json artifact-root
```

Require status `PASS`. The emitted `candidateIdentitySha256` is the join key
for every subsequent request, result, batch, shadow event and final report.
The artifact root becomes read-only for the evidence run.

## 3. Close the no-write mapping and identity layer

Produce a canonical synthetic snapshot and request without calling the engine:

```console
php tools/verify_thp_pairing_request.php request.json original-snapshot.json
```

After the isolated adapter calls the candidate engine, bind the complete
result back to the same request and candidate:

```console
php tools/verify_thp_pairing_result.php request.json original-snapshot.json candidate.json artifact-root result.json
```

Immediately before any test transaction, rebuild the snapshot from a fresh
database read and verify both revision and canonical hash:

```console
php tools/verify_thp_precommit_guard.php request.json original-snapshot.json observation.json fresh-snapshot.json
```

No command in this section authorizes a write. A stale revision/hash or an
identity mismatch discards the complete result.

## 4. Exercise isolated database boundaries

Use a disposable database cloned only from synthetic fixtures. Produce and
verify the complete success/failure matrices:

```console
php tools/verify_thp_transaction_probes.php transaction-probes.json
php tools/verify_thp_recovery_probes.php recovery-probes.json
```

Require `GO` from both. The transaction batch includes one success and an
injected failure after every required write stage. The recovery batch includes
crash-before-commit, crash-after-commit, superseded completion and duplicate
delivery. Every failed path must restore the exact allowed state and publish
nothing.

## 5. Exercise exact product behavior

All following batches are generated by the exact product harness and retain
the same candidate, source and migration identity:

```console
php tools/verify_thp_mode_probes.php mode-probes.json candidate.json artifact-root
php tools/verify_thp_performance_probes.php performance-probes.json candidate.json artifact-root
php tools/verify_thp_rating_import_probes.php rating-import-probes.json candidate.json artifact-root
php tools/verify_thp_operator_workflow_probes.php operator-workflow.json candidate.json artifact-root
php tools/verify_thp_runtime_configuration_probes.php runtime-config.json candidate.json artifact-root
```

Require `GO` from every command. These reports respectively prove:

- declared FIDE-system routing with no legacy/manual fallback;
- the full pre-write path at every declared system/size under explicit budgets;
- current rating-list import, reconciliation, idempotence and rollback;
- the chained English operator workflow and linked help;
- external configuration injection, least-privilege scope and redaction.

The verifier only checks supplied records. For each `GO`, retain the harness
log showing that the exact product route was actually exercised; otherwise the
report is a format check, not product evidence.

## 6. Run non-mutating shadow observation

Shadow starts only after sections 1-5 pass and privacy/operations review is
recorded. It cannot publish pairings, alter the primary response or trigger a
primary retry:

```console
php tools/verify_shadow_evidence.php shadow-manifest.json shadow-events.ndjson --minimum-turns=N
```

Require `GO`, the declared denominator, complete feature coverage, zero
blocking outcomes and a hash match for the immutable event stream. Any
candidate change starts a new stream; do not append across identities.

## 7. Re-scan the exact distribution

Scan the exact installer/source/runtime root delivered to TEC:

```console
php tools/scan_distribution_secrets.php DISTRIBUTION_ROOT
```

Require status `PASS`, then perform the separate private owner review. A
heuristic scan cannot waive rotation of a credential found in an earlier
candidate. Rebuild and restart the identity if any packaged artifact changes.

## 8. Package and promotion audit

Before calling the evidence bundle complete, verify all of the following:

1. every report is promoted from a parsed `.tmp` file and has a recorded
   SHA-256;
2. every identity-bearing report contains the single expected
   `candidateIdentitySha256`;
3. source commit, migration manifest and candidate artifacts are identical
   across the complete run;
4. no report has status `NO_GO`, `ERROR` or `REVIEW_REQUIRED`;
5. PTC and RTG cross-tests, corpus/acceleration gates and the controlled
   environment refer to the same final non-RC package;
6. unsupported records/features remain explicitly fail-closed in the product,
   manual and application scope;
7. owner-only administrative inputs, SDPC/TAPC order and TEC correspondence
   are tracked separately from technical evidence.

Finally run:

```console
php tools/verify_submission_readiness.php
```

`NO_GO` remains the correct result until every required gate in the
machine-readable ledger is genuinely closed. Updating prose, this runbook or a
verifier never closes a product, corpus or external gate by itself.

## Abort and resume rule

On a crash, interruption or operator stop, preserve the entire run directory.
Resume only an explicitly resumable harness step whose identity and atomic
output rules prove idempotence. Otherwise create a new run ID. Never relabel a
partial or superseded batch, never merge reports by filename alone, and never
use production state to fill an evidence gap.
